### 第 5 条的根因（两个，一个已修一个待定）

**A. 数据链断了（已修，一行）**
`apps/server/internal/store/catalog_repo.go` 的 `LoadCatalog`：

```sql
-- 写的时候带了 icon_reason
INSERT INTO pack_catalog_items(...,icon_status,icon_reason) VALUES(...,?,?)
-- 读的时候没带 —— 于是"为什么没有图标"永远是空字符串
SELECT item_id,evidence,source,model_path,icon_status FROM pack_catalog_items ...
```

迁移 `0026_catalog_item_icon_reason.sql` 的注释写着"之前原因算完就丢，界面只能给一个没有解释的占位格"，
结果 SELECT 漏列，等于原因**还是**丢了。补上 `icon_reason` 后，73 个缺图物品立刻说得清：

| 原因 | 数量 | 是什么 |
|---|---|---|
| `unsupported_model` | 62 | 方块实体类：箱子 / 床 / 旗帜 / 潜影盒 / 头颅 / 装饰陶罐 / 切石机 / 潮涌核心 |
| `requires_tint` | 10 | 颜色由游戏运行时决定：树叶 ×8、草方块等 |
| `missing_texture` | 1 | 缺贴图文件（盾） |

**B. 渲染器能力缺口（待定，未做）**
这 73 个物品**有** item model 文件，但模型是 `builtin/entity`（方块实体）或需要生物群系着色，
当前的图标生成只走 item model 路径 → 渲染不出来。
要真正补上，需要后端在遇到这两类时**回退到 blockstate → block model 渲染**
（`renderBlockModel` 已经存在，`blocks` 表里 1062 个方块也都有 blockstatePath）。
这是一次独立的渲染器改造，本轮未动。

### 第 7 条的「标签可读名」

后端只在标签恰好一个成员时才给真译名（`labelSource='single_member'`，331 个里只有 29 个），
其余 302 个的 `displayName` 是 `#ns:path` 形式 —— 对用户等于没有名字，
于是「任意木板」只能显示成 `#minecraft:planks`。

前端补了一层派生（`recipeView.tagLabel`，纯展示、不改数据）：

1. 有真译名 → 直接用；
2. 否则拿成员的显示名求**最有代表性的公共后缀**（基准取最长名，覆盖 ≥80% 成员即可）；
   必须这样放宽，因为原版标签的成员名并不整齐 ——「橡木木板 … 竹板」里有一个异类，
   严格求交会把「木板」一路降级成「板」；
3. 推不出（< 2 字）→ 用标签 id 末段兜底。

效果：`#minecraft:planks` → **木板**，`#minecraft:wooden_slabs` → **木台阶**。
另外把散落的候选角标降噪了：平时只留一个点，悬停/选中才展开 `n/m` —— 木桶有 8 个标签槽，
8 个 `1/11` 并排说的其实是同一件事。

## 二、只记录（本轮不动）

### 1. 链路透镜（C）有 62 条重复 React key

- **位置**：`apps/web3/src/chain/ChainView.tsx:72` → `key={`${node.id}-${node.depth}`}`
- **现象**：同一 depth 上出现同一个物品的多个实例（从不同路径到达同一层），
  例：`minecraft:acacia_planks-1` 撞车
- **后果**：React 的原文是"子节点可能重复或被丢弃，行为不受支持" —— 渲染结果不可信
- **修法方向**：key 里带上路径（父节点链）而不是只有 `id + depth`
- **归属**：`chain/` 整个目录仍是未跟踪状态，来自上一轮会话未提交的产物，不是本轮引入

### 2. 关系态链路本身

用户在反馈里提到「这个链路里面的东西也是存在问题的」，但没有细化现象。
需要指出具体是**下钻路径**、**方向切换后的内容**、还是**链路断点的判定**，才能定位。
