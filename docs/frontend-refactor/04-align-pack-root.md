# 对齐：包根目录方案（2026-10-04 第四轮反馈）

> 本文是**理解对齐，不是施工方案**。先确认我听到的和你说的东西一致，再动手。

## 0. 先回答你问的：右键菜单是不是点哪都一样

不是内容一样，是**覆盖面太窄**。全站 8 套菜单，内容逐一套对过，各不相同：

| 右键位置 | 菜单内容 |
|---|---|
| 模组行 | 重新解析 / 移动到分类▸ / 从包中移除 |
| 分类标题 | 重命名分类 / 解散分类 |
| 列表空白区 | 新建…（新建目录 / 添加模组） |
| 物品（网格 / 表格） | 看合成 R / 看用途 U / 看逆向链路 C / 设为焦点 / 看速览配方 / 复制 ID / 复制名称 |
| 任务节点 | 编辑这个任务 / 删除任务 |
| 画布空白 | 在这里新建任务 / 适应窗口 / 回到 100% |
| 章节行 | 在编排态打开 / 重命名 / 上移 / 下移 / 删除章节 |
| **全局兜底** | 切视图 / 命令面板 ⌘K / 复制整合包 ID / 复制当前地址 |

体感「点哪都一样」的来源：上面 7 个位置之外，**任何地方右键都落进全局兜底菜单**
（`app/GlobalContextMenu.tsx` 挂在 document 上）。目录树节点、日志窗口、详情区、
面板顶栏、状态栏……点出来的都是同一份「命令面板 / 复制包 ID / 复制地址」。

所以要做的是**补覆盖面**，不是改组件：每个对象类型给自己的菜单，
兜底菜单收窄到真正与光标下对象无关的那几个动作。

## 1. 页面布局：取消「来源」的上下分屏

**我听到的**：现在「来源」面板被切成上下两屏——上面是这个包里已有的内容
（原版行 + 已装模组分组 + 内容目录状态），下面是搜索/版本详情那一块。
你不想要这个拆分：**一个列表就该把包里的东西全列出来**，不要上下列两块。

**我的理解**：
- 「来源」这个面板整体会被第 3 条替代掉（见下），所以这一条实质是在定
  **替代它的那个视图长什么样**：单一列表，行内直接展开细节，不再有「下半屏」
  承载搜索结果或版本表。
- 搜索（添加模组）不再占同一个面板的下半部分——它是另一件事，
  应该走独立的入口/弹层，而不是常驻在列表下面。

**要你确认**：搜索结果你希望出现在哪里？（a）独立弹层/抽屉，
（b）仍是左侧列表里的一种临时视图（列表整体换成结果，可返回），
（c）别的。

## 2. 后端：包 = 项目，靠一份依赖文件描述

**我听到的**：新建一个包 = 新建一个项目。项目里维护一份**依赖文件**，
它约束并记录：装了哪些模组、配了哪些配方、任务书改了什么。细节待设计。

**我的理解**：你要的是一份**声明式的、可版本控制的清单**，而不是现在散在
SQLite 各张表里的状态。它至少记三件事：

1. **装了什么**：模组（来源平台 / projectId / 锁定的 versionId / sha1 / 是否必装）
2. **改了什么**：自建内容 —— 配方、结构、矿脉（后端 `validContentKind` 现在只认这三种）
3. **编了什么**：任务书（章节 / 节点 / 前置关系）的草稿

**现状（事实）**：后端目前是 `packs` / `pack_mods` / `catalog_generations` /
`content_documents` 多张表分散存，没有单一清单文件；
`packs.config_revision` 只在「可能影响目录的动作」上递增，用来判目录是否过期。

**要你确认**（这几条决定后端工作量）：
- 这份清单是**落盘的文件**（类似 packwiz 的 `pack.toml`、mrpack 的 index），
  还是**数据库里的一张表**读出来序列化？落盘 → 能被 git 管、能手工改、要处理冲突；
  落库 → 和现在一致，只是多一个导出视图。
- 「约束」这个词你想的是**声明式**（写下期望，工具去对齐现状），
  还是**记录式**（只记实际发生了什么）？两者后端差别很大。

## 3. 整体方案与样式：包根目录取代「来源」

**我听到的**：用新加的「包根目录」这套管理方案**整个取代**「来源」；
主题色等视觉保持与现在一致（不要因为换方案配色也跟着变）。

**我的理解**：
- 侧栏根节点的语义从「来源」（一个工具面板）升级为「这个包本身」——
  根 = 包，下面挂它的三类内容。
- 视觉不重新设计：沿用现有 `--mc-*` 令牌、`.p-row` 行样式、主题（浅/深）。
  换的是结构，不是皮肤。

## 7. 澄清（你第二次纠正）：职责统一的按钮，不是一棵树

> 上一版我理解偏了：你在说的不是「目录树里放几项」，而是**侧边栏每个按钮的
> 职责要统一** —— 一个按钮一件事，不要一棵上下折叠的树。这条取代 §4 与 §6。

**左侧竖轨，四个按钮，从上到下：**

| # | 按钮 | 职责 | 备注 |
|---|---|---|---|
| 1 | 项目管理 | 所有编辑都在这个里面做 | 模组列表、配方/结构/矿脉、任务书编辑都归它；单一列表，不再上下分屏 |

| 3 | 任务书 | 直达任务书 | 在项目管理里也能编辑，按钮只是直达 |

## 8. 再澄清：六区骨架，侧边栏 ≠ 主编辑区（**这条是口径基准**）

> 我上一张图只画了 3 个区域，把「侧边栏」和「主编辑区」合成了一块 —— 错的。
> 你描述的四个按钮是**第 2 区（侧边按钮栏）**的内容；我说的「包/内容列表」
> 是**第 3 区（侧边栏）**，它跟主编辑区是两个区域。

**六个模块（`app/AppFrame.tsx` 现有分层，代码里逐一对得上）：**

| # | 模块 | 组件 | 职责 |
|---|---|---|---|
| 1 | 顶边栏 | `TopBar` | 包信息；右侧放自建内容 / 构建 / 运行 |
| 2 | 侧边按钮栏 | `IconRail` | 4 个按钮：项目管理 / 新增模组 / 任务书 / Get Version |
| 3 | 侧边栏 | `ToolPanel` | **随第 2 区的按钮切换内容**：包内容列表 / 搜索结果 / 章节列表 / 版本 |
| 4 | 主编辑区 | `EditorArea` | 侧边栏里选中的条目，在这里编辑 |
| 5 | 底边栏 | `BottomDock` | Log；平时不显示，可唤起额外的底部菜单栏承载额外内容 |
| 6 | 状态栏 | `StatusBar` | 常态信息 |

**关键关系**：第 2 区是「选哪一类」，第 3 区是「这一类的清单」，
第 4 区是「清单里选中那一条的编辑区」——三者是递进的选中关系，不是并列面板。

**要你确认**：第 6 个是不是状态栏？你列的五条里第 5 条括号提到的
「额外的底部菜单栏」我理解成底边栏唤起的第二层，不是独立的第 6 区。
