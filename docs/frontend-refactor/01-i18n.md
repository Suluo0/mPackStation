> 关联：`docs/frontend-refactor/00-plan.md` 第 7 节 B6。
> 用户要求：本轮一起做完，不留口子。

---

## 1. 选型结论（已验证）

**前端：i18next 25.x + react-i18next 16.x。**

| 库 | 体积 | 类型安全 | 判断 |
|---|---|---|---|
| **i18next + react-i18next** | ~6–9 KB | 配 `i18next.d.ts` 增强 | **选它**：生态最大、提取工具链（`i18next-parser`）最成熟 |
| typesafe-i18n | ~1 KB | 编译期生成，最强 | 生态小、ICU 弱；本项目不差这几 KB |
| LinguiJS | ~2 KB | 编译期宏 | 需 babel/swc 插件，接入成本高于收益 |
| next-intl / react-intl | — / ~20 KB | — | Next 专用 / 体积大，本项目不合适 |

（来源：2026 年多篇 React i18n 横向评测，检索于 2026-10-04。i18next 周下载 3.5M+，是事实标准。）

选择理由聚焦一点：本项目的痛点不是省几 KB，而是**把散落的硬编码文案统一收编**。这依赖提取工具能从现有代码里扫出 key，`i18next-parser` 在这件事上最成熟。

**后端：不做翻译层，只返回 `code + args`。**

| 方案 | 判断 |
|---|---|
| 后端按 Accept-Language 返回整句 | **否决**。理由：① UI 文案本质是前端资产；② 本项目前后端同机单用户，「按语言返回」收益≈0 却把语言状态拆成两份；③ 后端给整句会破坏混排（如「Mekanism 仅支持 Forge / NeoForge」里模组名要加粗、加载器要变色）；④ 前端单测要 mock 后端字典 |
| 后端返回 `code + args`，前端翻译 | **采用**。前端是唯一翻译层，语言包是唯一事实源；后端不需要感知语言；日志/CLI 保持英文不受影响 |

## 2. 目标结构

```
apps/web3/src/i18n/
├── index.ts            i18next 初始化（语言检测、fallback、命名空间注册）
├── react-i18next.d.ts  类型增强（key 自动补全、错 key 编译报错）
└── locales/
    ├── zh-CN/
    │   ├── common.json     通用：确定/取消/保存/删除/搜索/加载中/无数据
    │   ├── panels.json     面板：商店/来源/构建/任务书/运行
    │   ├── editor.json     编辑器：索引态/关系态/规则卡/任务书节点
    │   ├── dock.json       底边栏：日志/健康/问题
    │   └── errors.json     后端 code 对应的消息模板
    └── en-US/  （同结构，先建骨架，内容后补）
```

## 3. Key 命名规范

- 格式：`域.对象.语义`，全小写下划线，例：`store.search.placeholder`、`mods.row.missing_dependency`。
- **禁止拼接**：不得 `t('mod.' + kind)`，必须写全 key（否则提取工具扫不到、改名即失效）。
- **插值用命名参数**：`t('mods.row.missing_dependency', {mod: 'JEI'})`，禁止 `{0}` 位置参数。
- 复数走 i18next 的 `_one` / `_other` 后缀，不手写三元。
- `title` / `placeholder` / `aria-label` 一律要走 key，这是最容易漏的地方。

## 4. 实施步骤

| 步 | 动作 | 判据 |
|---|---|---|
| 1 | `npm i i18next react-i18next i18next-browser-languagedetector`；devDeps 加 `i18next-parser` | 装好 |
| 2 | 写 `i18n/index.ts`：语言检测（先 localStorage、再系统语言）、fallback `zh-CN`、预加载命名空间 | 启动不报错 |
| 3 | 写 `locales/zh-CN/*.json` 骨架（先空对象） | 文件在 |
| 4 | 写 `react-i18next.d.ts` 类型增强 | `t('不存在的key')` 编译报错 |
| 5 | 在 `main.tsx` 挂 `I18nextProvider`（或直接在 index 里 init 后 import） | 生效 |
| 6 | **按文件迁移**：`panels/` → `editor/` → `app/` → `components/`，逐文件把中文抽成 key | 每迁完一个 `tsc --noEmit` 0 错 |
| 7 | 跑 `i18next-parser` 反查遗漏 key（未翻译/未使用） | 清单为空 |
| 8 | 建 `en-US` 骨架，先让结构存在（内容可后补） | 目录在 |

### 4.1 迁移时的两条硬规则

1. **一个文件迁完就跑一次 tsc**，不要攒着 —— 中文散在 JSX 文本节点里，漏一处就漏一条。
2. **混排句子必须拆**：`Mekanism 仅支持 Forge / NeoForge` 不能整句塞进语言包，要写成
   `t('store.fallback.only_loaders', {name: 'Mekanism', loaders: 'Forge / NeoForge'})`，
   否则之后加粗/变色做不了。

## 5. 后端侧：错误码化（本轮范围）

| 步 | 动作 |
|---|---|
| 1 | 盘点后端返回的中文消息（错误、冲突诊断、解析报告、任务状态） |
| 2 | 定义统一错误结构：`{code: "mod.missing_dependency", args: {mod, dep}}`，**保留原有中文到 `errors.json` 里做 zh-CN 文案**，界面观感不变 |
| 3 | 前端 `errors.json` 按 code 提供模板，渲染时插值 |
| 4 | 后端日志/CLI 不受影响，保留中文或英文均可 |

**范围控制**：本轮只做「结构切换 + zh-CN 文案搬迁」，**不要求后端同步产出 en-US**。这样界面零变化、风险可控，英文是之后加语言包的事。

---

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 中文量大，一次性抽完容易漏 | 按目录分批，每批 tsc + 真浏览器抽查一屏 |
| 模板字符串拼接导致 key 扫不到 | 规范里明令禁止；`i18next-parser` 扫完后人工核一遍遗漏清单 |
| 语言包与代码不同步 | 把 `i18next-parser --dry-run` 纳入验收步骤 |
