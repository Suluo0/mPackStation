## 4. 验证边界（两套验证各自证明了什么）

1. **两套验证分工，别再混着读**。
   `scripts/chain-test-run.sh` + `scripts/chain-test.py`（173 例，端口 18872/18873）走的是**协议桩**：
   桩按 `launcherCore/src/cli.rs` 的 clap 语义校验 argv、按 `protocol.rs` 回 JSON Lines 事件、按
   `install.rs` 回 `version_id`，不下载文件、不起游戏——它证明的是「前端请求 → 同步校验 → 入队 →
   入库 → worker → fork/exec → 终态收敛」，选桩是因为这轮要每轮快跑，下载几十上百 MB 跑不起。
   `scripts/verify-terminal-chain.sh --launch`（43 条断言，端口 18874，`MPACK_LAUNCHER_BIN` 指向
   cargo 真编译出来的 `mpack-launcher`）才是**真内核**：真下 Modrinth jar、真装 libraries/assets、
   真起 Minecraft。两边都是绿，但结论层次不同。归档的那份终局证据是 **O25 修完之后重新构建服务端再跑的一轮**
   （21:27，43/43），不是更早的 20:06 那轮——两套绿都落在同一份代码上。
2. **「游戏起来了」判定到哪一步**：安装任务终态 `success` + 实例目录里 manifest 每条 jar 的 sha1
   复核 + 版本 JSON 声明的库全部在位（O16 守护）+ 进程存活 + 游戏日志本轮段落里出现 Fabric 横幅
   与 `Setting user`，且没有 `Mod resolution failed`。**没有**做"进到主菜单/截图/实玩"级别的判定，
   离线账号那条 authlib 401 告警属预期。
3. **残余缺口**：O16 的后半、O17、O18、O19 只有端到端守护，没有专门的 Rust 单测（Java 布局探测、
   执行位、竞速下载残留 partial 这三条都能写成单测，值得补）；O20 闸门只挡权威装配路径，
   调用方显式带 `files[]` 构建（前端正常不走这条）不经过闸门。
4. `.mrpack` 的合规性按 v1 规范校验（`formatVersion=1`、`dependencies.minecraft/fabric-loader`、
   `files[].path/hashes/downloads/fileSize`）。`sha512` 现在有真值：provider 解析带上 sha512，
   终局验证断言每条 `files[]` 都带 sha1+sha512。
5. 全部测试只碰 `/tmp/mpack-chain`、`/tmp/mpack-chain-nobin`、`/tmp/mpack-terminal` 与端口
   18872/18873/18874/5273；用户开发库 `/tmp/mpack-data` 与 5173/18765/18766/18871 全程未触碰。
