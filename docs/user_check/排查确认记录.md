### 1. 右键菜单区域处理 —— 用户观察属实，"切到表格视图"确实会出现在左侧边栏

**结论：右键菜单目前只做到了"对象级"区分（行/节点级），没有做到"区域级"区分（栏/面板级）。左侧边栏右键出现「切到表格视图」属实，根因是全局兜底菜单只看当前模式（mode）、完全不看点击位置。**

菜单体系是两层的：

- **区域/对象专属菜单**：模组行、章节行、画布节点、索引行、物品格都有自己的 `onContextMenu`（`apps/web3/src/panels/SourcesPanel.tsx:490-507`、`QuestPanel.tsx:152`、`QuestCanvas.tsx:232,312`、`ItemGrid.tsx:97`、`ModeIndex.tsx:183,208`），它们 `preventDefault` 后全局菜单会让位。
- **全局兜底菜单** `GlobalContextMenu`（`apps/web3/src/app/GlobalContextMenu.tsx`）：挂在 `document` 上，凡是没有被上面那些接住、且不在输入框里的右键，全部落到这里。「切到表格视图 / 切到网格视图」的追加条件只有 `mode === 'index'`（`GlobalContextMenu.tsx:45-51`），与光标在哪个区域无关。

具体到左侧边栏：最左边的图标栏 `IconRail`（`apps/web3/src/app/IconRail.tsx:18-27`）完全没有绑定 `onContextMenu`，右键直接冒泡到 document 被兜底菜单接住；左侧工具面板的行与空白区虽有专属菜单，但面板标题栏等部位同样落空。所以用户在左侧边栏右键看到「切到表格视图」。

**矛盾点**：兜底菜单的注释（`GlobalContextMenu.tsx:42-43`）自称只放"跟光标下对象无关"的动作，但「切到表格视图」实际是索引模式主编辑区的视图动作，并不是"任何位置都成立"——它被放进兜底菜单本身就是越界。

**修复方向提示**（供后续改）：把视图切换从兜底菜单挪到索引区/EditorArea 区域级处理，或给兜底菜单增加区域判断（按 `e.target.closest()` 判断落点区域再组装菜单项）。

### 4. Windows 应用默认配置存放路径 —— 对齐业界：放 AppData\Roaming，不是 Documents

**结论：应用默认配置应放 `%APPDATA%\<AppName>\`（AppData\Roaming），与 VS Code / Electron / Tauri 生态一致；Documents 只放用户主动保存的工程与文档，且项目目录应允许用户自选。**

调研依据（微软官方 + 业界案例）：

- 微软 [Known Folders 文档](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)：`RoamingAppData` 放每用户设置（小体积、随漫游配置跨机同步）；`LocalAppData` 放缓存和机器相关大文件；`Documents` 官方定位是"用户文档库"，不是应用配置位置，且常被 OneDrive 重定向，业界没有把配置放这里的做法。
- 业界案例（均为 Roaming，缓存类才用 Local）：VS Code 用户设置在 `%APPDATA%\Code\User\`（[官方文档](https://code.visualstudio.com/docs/getstarted/settings)）；Electron `userData` 默认就是 `%APPDATA%\<应用名>`（[app API](https://www.electronjs.org/docs/latest/api/app)）；Tauri 的 directories 约定 config/data → Roaming（[ProjectDirs](https://docs.rs/directories/latest/directories/struct.ProjectDirs.html)）；Chrome/Edge 大体积 User Data 放 Local（[Edge 策略](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies#userdatadir)）。
- 三端对齐建议：Windows `%APPDATA%\<AppName>` / macOS `~/Library/Application Support/<AppName>`（[Apple 指南](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/MacOSXDirectories/MacOSXDirectories.html)）/ Linux `~/.config/<appname>`（[XDG 规范](https://specifications.freedesktop.org/basedir-spec/latest/)）。
- **项目/工程文件**（用户主动创建的、类似 Maven/Gradle 项目目录的东西）：默认给 `Documents\<AppName> Projects`，但像 IDE 一样允许用户自选目录——这正好回答了原清单 #8 里"项目目录放哪"的一半。

### 5. 中文搜索失效 —— 属实，且比用户感知的更严重：整个模组搜索都失效了（不只是中文）

**结论：模组搜索当前对任何关键词都返回空（英文也一样），后端搜索管线故障，与网络无关。"中文搜不到"只是这个故障的一个表现。**

在验证包-0025（1.21.1 · Fabric）上实测（2026-10-04，开发实例 18872/5271）：

- 商店面板搜「通用机械」→「没有命中。设置页确认 CurseForge Key 后再试。」
- 商店面板搜「Mekanism」（英文）→ 同样零命中。**英文也搜不到，排除"只是中文问题"。**
- 直接 curl 后端：`GET /api/packs/<packId>/mod-search?q=Mekanism&limit=5` → `{"items":[],"errors":{"curseforge":"not_configured","modrinth":"unavailable"},"total":0}`
- 但本机直连 Modrinth 官方 API 完全正常：`https://api.modrinth.com/v2/search?query=Mekanism` → HTTP 200，第一条就是 Mekanism。

即：后端把 Modrinth 报成 `unavailable`，而真实网络可达——问题在后端搜索代码本身（时间线上高度可疑的改动是 10-02/03 的 6c0aa5d「模组搜索别名排序」，根因细节待后端排查结果补充）。

另注：即便搜索修好，Modrinth/CurseForge 的 API 本身没有中文名数据，「通用机械」命中 Mekanism 需要自建中文别名/译名层（数据来源与表结构待后端排查结果确认）。

### 6. 输入框"不能输中文" —— 输入框本身不背锅：实测中文能输入、能保留；代码层无 IME 拦截

**结论：输入框没有输入限制，中文可以输进去并保留；"拼音搜不到"是搜索能力缺失（还没有拼音索引），不是输入框问题。**

实测证据（同包同日）：

- 商店面板搜索框输入「通用机械」→ 值保留在框内（上面 #5 的实测过程即证）。
- 索引模式搜索框输入「刷怪蛋」→ 正常进入 URL（`?q=刷怪蛋`），目录正常过滤出 80 条刷怪蛋。**索引搜索的中文匹配是好的**（目录数据里有中文名）。

代码证据（apps/web3）：

- 全站搜索框唯一入口 `SearchInput`（`src/ui/SearchInput.tsx:23-25`）是标准受控 input，`onKeyDown` 只处理 Enter，无任何按键过滤/正则清洗。
- 索引搜索框（`src/editor/ModeIndex.tsx:114-115`）同样是标准受控 input，值走 URL 状态；`url.ts` 用 `URLSearchParams` 标准编解码，对 CJK 安全。
- 全局热键（`src/app/useHotkeys.ts:21,33`）在 `typing`（INPUT/TEXTAREA/SELECT/contentEditable）时一律放行，不会打断输入法。
- 未发现 `compositionstart/end` 处理、`preventDefault` 字符键、ASCII 过滤等任何 IME 杀手写法。

保留项：CDP 自动化无法完全模拟真实输入法组合键（composition）过程，若用户仍能稳定复现"拼音打不进框"，需要人工在浏览器里复验一次；但受控值管线本身干净，且「不能拼音搜索」的真正原因就是拼音索引还没做（对应原清单 #15 需求）。

### 9. 自建内容盘点 —— 用户说"只能新建配方"基本属实：后端支持三种，但 UI 只露出一种（结构/矿脉没有切换入口）

**结论：后端自建内容枚举为 配方 / 结构 / 矿脉 三种，但前端没有任何切换种类的入口，`?ck=` 参数没有 UI 写入点，用户永远只能看到默认的「配方」——结构、矿脉成了"藏在 URL 后面的功能"。另外任务书（创建任务书/新建章节）也是自建内容，用户可能没把它算进去。**

证据：

- 后端只认三种：`validContentKind(k) { return k == "recipe" || k == "structure" || k == "ore" }`（`apps/server/internal/service/content.go:293`），其余一律 422。
- 前端种类表与后端对齐：`KINDS = {recipe: 配方, structure: 结构, ore: 矿脉}`（`apps/web3/src/panels/ContentPanel.tsx:12-16`）。
- 但种类取值是 `const kind = ck ?? 'recipe'`（ContentPanel.tsx:21），`ck` 来自 URL 参数；全代码 grep `ck:` 的 patch 写入点——**没有任何 UI 控件写它**。面板上只有一个「新建」按钮（ContentPanel.tsx:51），无种类切换 tab/下拉。实测点开顶栏「自建内容」：左栏只显示"配方 0 · 还没有配方。点「新建」建一份草稿。"，与用户描述一致。
- 要新建结构/矿脉目前只能手改地址栏 `?ck=structure` / `?ck=ore`。
- 其余可创建的东西：任务书（`QuestPanel.tsx:80` createBook、`:106` addChapter——创建任务书、新建章节）。
- 索引工具栏没有新建入口；魔改模式（ModeEdit）grep 不到"新建/创建"。README 宣传的"标签/多语言目录"等编辑能力没有自建（新建）性质的动作，进度树画布是展示性质的。

**修复方向提示**（供后续改）：给 ContentPanel 加种类切换（三个 tab 或下拉），一行状态即可把藏在 URL 里的两种能力放出来。

### 2. Minecraft 解析产出 —— 数据是齐全的：物品、图标都在库里；"只见配方+metadata"是前端面板的种类语义造成的观感

**结论：原版解析链路完整且产出齐全（live 库实测 1330 物品、1330 图标全部 ready）。"没有物品"是因为解析器本来就不产「物品」这个 kind（物品以 item_model 存在），而 web3 把 item_model/texture/lang/item_icon/metadata 全部折进"资源"组——玩法内容组里自然只剩配方、进度、结构这些。"图标没解析"同样不成立：图标是目录重建时实时渲染合成的，1330 张全部 ready。**

解析链路与实测数据（2026-10-03 的成功 run，13318 个文件）：

- 链路：`POST .../mods/{modId}/content/parse`（`routes_mod_content.go:24`）→ `mod_content_task.go:145`，原版分支拉 Mojang 客户端 jar（磁盘缓存）+ zh_cn 语言；分类规则在 `mod_content_kind.go:52-102`（`data/`→recipe/advancement/loot_table/structure/worldgen/tag，`assets/`→item_model/lang/texture）。
- 产出：recipe 1290、item_model 4953、texture 3070、advancement 1399、loot_table 1178、item_icon 1417、tag 530、worldgen 862、structure 34、lang 2、**metadata 1**。
- 物品（目录口径）：catalog-v4 明确把原版物品算进来——语言键 `item.*` 为权威来源（`item_catalog.go:184-188`），实测 `pack_catalog_items` 1330 条全部 `minecraft:` 命名空间；右侧网格能看到这 1330 个物品（本记录 #7 实测同证）。
- 图标：目录重建时由渲染器从模型+纹理实时合成（`item_catalog.go:722,764-796`），PNG BLOB 入 `pack_catalog_item_icons`；缺失图标必须带原因（0026 迁移）：unsupported_model / missing_texture / requires_tint / runtime_generated_model（实体类共 73 个 missing 属已知未做）。

为什么用户会看到"只有配方 + 一个 metadata"：

1. **种类语义**：`SourcesPanel.tsx:43,51` 把 item_model/texture/lang/item_icon/metadata 归为"资源"折叠组，第一组"玩法内容"里原版只剩配方/进度/结构/标签/地形/战利品等可点数——没有名为"物品"的行。
2. **时机**：当天目录 02:41-02:50 有多代 partial/重建记录，若用户正好在重建窗口看，目录确实是空/缺的。
3. **metadata 是什么**：原版没有 fabric.mod.json 这类描述符，解析器对原版手工造了一行（`mod_content_task.go:210-212`），payload 是 `{"loader":"builtin","modid":"minecraft","version":"1.21.1","source":"mojang:version_metadata"}` 四字段。它**本来就在后端库里**，由 `GET .../content?kind=metadata` 原样返回（`routes_mod_content.go:40-49`），前端把它当"元数据"种类渲染出来了（`SourcesPanel.tsx:45`）。

对用户"metadata 不应展示在前端、应送后端"的回应：**它已经在后端**；问题是前端把这个内部口径的种类当内容展示出来了。用户的直觉成立——"元数据"行对用户没有信息量，不宜作为内容种类出现在面板里（是否彻底隐藏、还是收进"资源"组不计数，属后续改造决策）。

### 3. 后端项目数据存储形态 —— 确认就是单个 SQLite 文件，磁盘上没有任何"项目目录"概念

**结论：用户的猜测属实——现在整个应用的数据就是一个 `mpackstation.db` 文件，包边界只存在于数据库键里（按 pack_id 分域），磁盘上没有每个项目一个 folder 的概念。**

- **单一 .db**：路径 = `{dataDir}/mpackstation.db`（`apps/server/cmd/server/main.go:57-62,84`，dataDir 由 `-data` flag 或 `MPACK_DATA` 环境变量决定）；打开逻辑 `store.go:49-80`（modernc.org/sqlite，WAL，单连接）。开发实例实际用 `/tmp/mpack-data`（`scripts/dev.sh:8`）；仓库内 `data/mpackstation.db` 是 09-19 的恢复快照，非活动库。注意：迁移实际已到 **0028**（未提交的新迁移文件），不只是 README 说的 27。
- **没有 per-pack 目录**：实测数据目录里只有 db、server.lock、runtime-token、`cache/minecraft-assets/`（原版 jar+语言缓存，按 MC 版本共享）。包删除级联、包隔离全靠 `(pack_id, ...)` 主键（migration 0021）。
- **其余落盘点全量**：.mrpack 产物写到用户批准的导出目录（`build.go:412-437`，`allowed_export_dirs` 表）；导入暂存 `{dataDir}/tmp`；模组 jar 字节不持久化（解析时现拉）；图标是库内 BLOB；`internal/blobstore` 包存在但从未接线。
- **应用级默认配置现状**：`config.go`（类 TOML 配置文件 + `MPACK_*` 环境变量 + flag 优先）；CurseForge key 在 DB `secrets` 表（设置页可管理）；平台可达性结果写 `settings` 表。都在数据目录/进程环境里，**没有走用户目录的标准配置位置**——这正是原清单 #10 要对齐 Windows 惯例时需要动的点。
- **改造评估（事实基础）**：天然属于单包边界、将来可搬进"项目目录"的：pack_mods/selections、mod_content、pack_catalog_*、catalog_generations、conflicts/locks/versions/artifacts/releases、任务书、各类包内证据表。天然跨包共享、应留全局的：mod_identity / platform_projects / platform_releases（平台元数据缓存）、jar_index（按 sha1 跨包去重）、file_objects（按哈希）、secrets/settings/onboarding_state、磁盘上的原版资源缓存。

### 5（根因补充）. 中文搜索失效的根因 —— 两个叠加：环境故障（当前真正原因）+ 未提交的代码回归（修好网络后会显形）

**结论一（当前故障）：运行中的后端进程挂着一个已死的本地代理，所有平台搜索请求出不了网——这才是"搜什么都命中不了"的直接原因，与 6c0aa5d 无关。**

- 实测：后端进程环境变量里有 `HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:52135`，该端口**无进程监听**；Go 的 HTTP transport 默认遵循代理环境变量 → Modrinth/CurseForge 请求全部失败，接口统一返回 `modrinth: "unavailable"`。本记录 #5 的直连测试（Modrinth 200 正常）与后端报 unavailable 的矛盾由此解释。
- 这个故障模式 `scripts/dev.sh:15-29` 的注释里就记载过（"看着像代码改坏了，实际是出不了网"）。**重启后端并清掉代理环境变量即可恢复**；建议 dev.sh 加代理存活检测。

**结论二（潜伏回归，未提交的工作区改动）：Fabric 包下搜中文别名会被双滤网彻底滤掉，网络修好后「通用机械」仍然搜不到 Mekanism。**

- 未提交改动新增：搜索注入包 loader（`mods.go:217-239`）、`injectSlugMatch` 的 loader 拦截（`mods.go:581`）、降级区打分门槛（`mods.go:359-365,391-396`）。
- 推演链：Fabric 包搜「通用机械」→ 别名表命中 mekanism → 但 Mekanism 只有 forge/neoforge 版，主结果注入被 loader 拦截 → 降级重搜后打分门槛 50 分，中文关键词对英文元数据只打 10 分 → 滤掉。已提交的 6c0aa5d 反而没有这个问题（无 loader 检查）；已验收的 ae2/精致存储都有 Fabric 版所以没暴露。
- 另一个硬事实：别名命中**不会被代入平台查询词**（`mods.go:450` 仍把中文原文发给 Modrinth，而平台 API 本身没有中文数据）；别名表是硬编码 Go map（`modsearch_alias.go:9-25`），库里没有别名表。**中文模组搜索要长期可用，需要：别名数据入库 + 把别名代入平台查询词（或 slug 直取）+ loader 白名单放行别名命中。**
- 修法提示（后端排查给出）：`otherLoaderRelevant` 对别名命中开白名单（aliasSlug 相等直接放行）。

### 8. Git 跟踪/提交能力 —— 用户感觉准确："Git"是图标隐喻，后端根本没有 Git；能跟踪的是库内版本链，不能提交是因为发布能力从未实现

**结论：后端没有用任何真实 Git（无 go-git 依赖、不调系统 git）。"Git"只是 web3 构建面板的分支图标隐喻。真实存在的是 SQLite 里的版本跟踪链（登记版本→锁定快照→构建产物→交付检查→发布记录），本地闭环完整可用；"不能提交"的准确边界是：发布到 Modrinth/CurseForge 是空壳，`HTTPAdapter.Publish` 恒返回 `ErrUnavailable`。**

- 图标隐喻出处：`docs/design/web3-ide-shell-v3.md:115`（"构建图标换成 Git 分支……版本/产物/检查/发布的语义载体"）、`apps/web3/src/panels/BuildPanel.tsx:13`。
- 可用的本地闭环（路由均在 `routes_publish.go`）：导出目录管理、交付检查、版本登记、`.mrpack` 构建（有冲突闸门/锁一致性闸门/目录批准闸门）、产物下载。
- 空壳部分：`POST .../publish/{provider}` 路由存在，但 `provider=="local"` 只把发布记录标成 succeeded、不上传任何东西（`publish.go:222-229`）；其他 provider 一律失败（`http_adapter.go:496-498` 恒 `ErrUnavailable`）。设计文档 `docs/issues/ISSUE-P7-BUILD-PUBLISH.md:38` 自己也标注"真实 CF/MR 网络仍需后续在线环境验证"——即真实发布从未实现。
- 对原清单 #7 的回答：用户说"有 Git 跟踪、不能提交"——现状就是这个隐喻与实现能力的落差。后续要么把"提交/发布"实现掉（需要平台凭证，README 已确认无凭证必须拒绝），要么在 UI 上把 Git 隐喻降级为"版本/构建"，避免误导。
