## 1. 目标与范围

**产物只有一个**：一个能被 `mPackLauncher` 装上、并且真的能玩起来的整合包（`.mrpack`）。这条已经跑通（`docs/tests/evidence/terminal-run-2026-09-30.log`，43 条断言全绿，Minecraft 1.21.1 + Fabric 0.16.14 起窗）。

**作者的心智只有四步**：

1. 这个包里**放什么**（模组）
2. 这些东西**怎么来、怎么改**（物品 ⇄ 合成 ⇄ 魔改）
3. 玩家**按什么顺序经历它**（任务书）
4. **出去**（检查 → 构建 → 安装 → 起窗 → 发布）

第 2、3 步操作的是**同一批物品 ID**。后端早就把它们连成了一张图：`catalog items` / `mod-content recipe` / `content doc` / `quest rewards` / `quest modRefs` 全部以物品 ID 与模组 ID 互相关联。前端却按接口切成了 5 个页面，于是作者每换一步就要重新找一遍同一个物品。

**范围**：只改前端 IA 与交互。**不改后端契约**（本轮只需要补 3 个前端 API wrapper，见 §9）。不做视觉改版，视觉以 `design-system.md` 为准。

**非目标**：FTB 完整导出 / SNBT / 真实存档写入；多包并行编辑；移动端布局；新后端域。

## 2. 减法判据

一条判据，只用这一条：

> **导航的每一项 = 作者的一个意图；不是一个后端域，也不是一个接口。**

按这条判据重数现状（`AppShell.tsx:27-38`）：

| 现有项   | 属于哪个意图              | 处置                 |
| ----- | ------------------- | ------------------ |
| 概览    | 判断「这个包现在怎么样、下一步干什么」 | **保留**             |
| 模组    | 放什么进去               | 并入「内容」的来源维度        |
| 物品    | 包里有什么               | 并入「内容」·索引态         |
| 合成    | 东西怎么来               | 并入「内容」·关系态         |
| 魔改    | 东西怎么改               | 并入「内容」·写态          |
| 模组内容  | 某个模组贡献了什么           | 并入「内容」的来源维度 + 类型筛选 |
| 依赖与冲突 | 判断「能不能出包」           | 并入「概览」，就地处理        |
| 任务书   | 玩家按什么顺序经历           | 并入「内容」·编排态         |
| 打包与发布 | 出去                  | 并入「交付」             |
| 启动器   | 出去（玩起来）             | 并入「交付」             |

**10 项 → 3 项**：概览 · 内容 · 交付。加上全局 2 项（工作台、整合包）与一个齿轮图标按钮，**可点导航项从 12 降到 5**，并且它们排在一条 48px 的顶栏上——横向空间有限，第 6 项会立刻显得拥挤，这是防止再次堆菜单的物理约束。

**为什么任务书并进「内容」而不是单列**（这是 v1 没敢做的一刀，也是你问的第 1、2 条）：

- 任务节点的目标与奖励**就是物品**，前置**就是配方链**。它不是另一个数据域，是同一批对象的另一种排布。
- 只有同页，「魔改完一条配方，顺手把它变成一条任务」才是一次点击而不是两次导航 + 一次手工重填（§7 链路 E）。分成两页时，作者必须把系统已经知道的信息（产物、材料、前置、图标）再抄一遍。
- 后端已经把这条路的存储和校验都做好了：`quest_nodes.mod_refs` 落库（`content_repo.go:347`），并且 validate 会报 `cross_pack_reference` / `missing_mod_reference`（`content.go:842-844`）。前端 `questNodeSchema.modRefs` 字段也在（`api/content.ts:106`），**只是没有任何编辑 UI**。缺的从来不是能力，是入口。

**取舍与退路**：编排态需要「章节 rail + 画布 + 图例」，比另外三态重。若实测发现同页切换让画布拥挤，退路是把编排态提升为第 4 项（`/packs/:id/quests`），**但焦点对象与「魔改 → 生成任务」的动作必须保持不动**——退的是导航层级，不是联动。

## 3. 目标 IA 与路由映射

**外壳是顶栏，不是左侧栏**（2026-10-01 用户拍板，v2.1 改动）。理由不只是审美：左栏是纵向的，加一项零成本，所以 v1→实现时从 7 项涨到了 10 项；顶栏是横向的，第 5 项就开始挤，**导航膨胀在物理上被封死**。这是结构性防呆。底边栏整个删除——它高 116px（`shell.css:81`），`.app-content` 还为它留了 136px padding（`shell.css:73`），删掉后腾出的高度远超顶栏吃掉的 48px。

```
┌────────────────────────────────────────────────────────────────────────┐
│ ◆ mPack   工作台  整合包 │ 包名 ›  概览  内容  交付 │   ⏳索引 62%  🔍⌘K  ⚙ │ 顶栏 48px
├──────────┬──────────────────────────────────────┬──────────────────────┤
│ 来源栏    │           画布（四态）                  │ ▣ 包状况              │
│ 模组/搜索 │  [索引] [关系] [魔改] [编排]             │  健康 82 · 告警 2     │
│ 解析状态  │                                      │  MC 1.21.1 · Fabric   │
│（默认折叠 │          焦点对象的画布                 │  v0.3.0 · 24 模组     │
│  56px）   │                                      │ ────────────────────  │
│          │                                      │ ▣ 当前焦点            │
│          │                                      │  物品/配方/模组/节点   │
│          │                                      │  传送门按钮（带参数）   │
└──────────┴──────────────────────────────────────┴──────────────────────┘
                ↑ 底边栏删除，其真实内容全部上移
```

顶栏三段（左→右）：

| 段 | 内容                                  | 说明                                                                          |
| - | ----------------------------------- | --------------------------------------------------------------------------- |
| 左 | 品牌 + 全局导航「工作台 `/`」「整合包 `/packs`」    | 永远存在，2 项封顶                                                                  |
| 中 | 面包屑 `包名 ›` + 包内三态 Tab「概览 / 内容 / 交付」 | **仅在有包上下文时出现**；用面包屑而不是分组标题（现状 `AppShell.tsx:110-112` 的「创作工具/包工作台」假分组标题一并删除） |
| 右 | 长任务胶囊（点开=任务抽屉）· ⌘K 搜索 · ⚙ 设置        | 全局动作，不放包上下文                                                                 |

右栏两段（上→下）：

| 段    | 内容                              | 说明                                                            |
| ---- | ------------------------------- | ------------------------------------------------------------- |
| 包状况  | 健康分环 + 告警数 + MC/loader/版本 + 模组数 | 从底边栏（`AppShell.tsx:140-165`）上移；**可折叠成一行**，焦点内容多时让位给 Inspector |
| 当前焦点 | 焦点对象详情 + 带参数传送门                 | 原 `InspectorRail`，保留并修好（见 §4.5）                               |

**内容页的「来源栏」是页内左列，不是应用级导航**：装模组清单 / 启停 / 钉版 / 解析状态 / 搜模组抽屉入口（原「模组」+「模组内容」两页的管理面）。默认折叠成 56px 图标条，展开 260px；折叠状态记 `localStorage`。编排态时它整体换成章节 rail。关系态画布自带的物品选择器（`RecipeBrowserPage.tsx:99-117` 的 `.rb-picker`）职责不同（选物品 vs 管模组），保留。

**外壳三件套已经存在，v2 是把它们接通，不是新建**：`FocusProvider`（`AppShell.tsx:82`）、常驻 `InspectorRail`（`:132`）、`CommandPalette`（`:166`）、包级目录缓存 `PackCatalogProvider`（`:83`，`key={activePackId}`）。

### 3.1 路由映射（旧路由一律 302 到新路由并带参数，不产生 404）

| 旧路由                        | 新路由                                                    | 说明                                                                    |
| -------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------- |

| `/packs/:id/tweak`         | `/packs/:id/content?mode=edit`                         | 写态                                                                    |

| `/packs/:id/publish`       | `/packs/:id/delivery`                                  | 交付                                                                    |
| `/packs/:id/launcher`      | `/packs/:id/delivery?step=install`                     | 交付·安装/起窗段                                                             |

**URL 是焦点的单一事实源。** `?item=<id>&mode=<态>&ns=<模组/命名空间>&type=<kind>&doc=<docId>&node=<nodeId>` 全部进 URL；`FocusContext` 只是它的内存缓存（现状 `FocusContext.tsx:33-52` 是纯 `useState`，刷新即丢焦 —— 这是必须修的实现细节，不是设计取舍）。判据：**任意状态刷新页面，焦点与所在态原样恢复**。

参数名沿用已实现的两个，**不新造同义词**：`?item=` 已由 `RecipeBrowserPage.tsx:32` 读取，`?ns=` 已由 `ItemCatalogPage.tsx:25` 读取（`PackPages.tsx:245` 的「贡献 N 物品」就在用它）。v2 只新增 `mode` / `type` / `doc` / `node` / `rail` / `step` / `panel`。

## 5. 交互准则（每条带判据 + 现状违反点）

1. **一屏一个焦点。** 任何时刻 Inspector 里那个东西就是「我正在做的东西」，切态不丢。
   判据：索引 → 关系 → 写 → 编排 来回切 4 次，焦点物品不变，且每态都以它为中心。
   现状违反：只有关系态读焦点（`RecipeBrowserPage.tsx:27-29`），其余 5 个写端全是单向漏斗。

2. **跳转即换视角，不是换目的地。** 禁止 `navigate` 到不带上下文的整页。
   判据：全仓 grep `navigate(` 的结果里，包内跳转必须带焦点参数或只改 `?mode=`。
   现状违反：`InspectorRail.tsx:99-104`、`RecipeBrowserPage.tsx:140`。

3. **读态与写态是同一对象的两面。** 看配方和改配方之间只有一个动作，改完立刻看得见。
   判据：关系态点「魔改此配方」→ 写态打开的正是这条 payload；apply 成功 → 关系态该配方立刻带「已魔改」标记，无需手动刷新。
   现状违反：关系态无写态入口；apply 不触发 catalog 刷新。

4. **能就地处理的绝不跳页。**
   判据：概览的冲突行上直接 resolve/ignore，处理后健康分、底部告警数、交付页的构建闸门三处同时更新。
   现状违反：健康右栏唯一动作是跳依赖页（`PackPages.tsx:208`），而依赖页只有整包重解析、没有行级动作。

5. **URL 是状态的单一事实源。** 焦点、态、筛选、文档、节点全进 URL。
   判据：任意状态刷新 / 复制链接给另一台机器打开，看到的完全一样。
   现状违反：`FocusContext.tsx:33-52` 纯内存；`ItemCatalogPage`/`RecipeTweakPage` 的选中态是页面 `useState`，离开即丢。

6. **长任务不打断当前工作。** 解析 / 重建 / 构建 / 安装都是后台任务，页面不阻塞、不白屏。
   判据：触发解析后立刻切到别的态做别的事，再切回来进度还在；底部状态条始终能看到「有 N 个任务在跑」。
   现状：解析轮询在页面内（`ModContentPage.tsx:216-245`），离开页面即丢进度 → 轮询上提到 context。

7. **错误贴在出错的地方。** validate / apply / build 的 issue 按 `path` 落到具体字段旁，不是全局 toast 一闪而过。
   判据：校验失败时，出错的 JSON 路径在编辑器里高亮，issue 列表点一条能定位到那一行。
   现状：写态已有 issue 列表（`RecipeTweakPage.tsx:266-273`），但未与编辑器行号联动。

8. **不留假 affordance。** 没有真实数据源或没实现的按钮不出现在界面上。
   判据：全仓 grep「后续版本提供」/「敬请期待」= 0 命中；每个按钮点下去都有真实后端调用或真实前端状态变化。
   现状违反：`PackList.tsx:77-89`、`TaskPanel.tsx:56`、`PackPages.tsx:468`、`AppShell.tsx:150`。

9. **空态必须指向下一个动作。**
   判据：每个空态文案里含一个可点的主按钮，且该按钮就是这一步该做的事（例：索引态无物品 → 「重建目录」；关系态未选物品 → 「从命令面板找一个物品」）。

10. **键盘可达。** Cmd/Ctrl+K 设焦点；方向键走物品网格；Enter 进关系态；`E` 进写态；`Q` 进编排态；Esc 回上一态；Delete 删节点/边（已有，`QuestBookEditor.tsx:558-585`）。
    判据：不用鼠标能完成链路 D（魔改一条配方）。

## 7. 使用者视角的交互链路

### A｜从空机器到玩起来（主干，首次上手）

1. 打开 `/` → 空态迎新（`OnboardingView`）→「新建整合包」→ 填名称 + MC 版本 + loader → 建包。
2. 自动落到 `/packs/:id`（概览）→ 上手清单胶囊提示「第 2 步：加模组」→ 点它。
3. 进「内容」→ 来源栏「添加模组」抽屉 → 搜 JEI → 选兼容版本 → 添加（真下 jar，触发解析任务）。
4. 底部状态条显示解析进度；同时可以在索引态浏览已有物品。
5. 解析完成 → 概览出现冲突信号（缺 fabric-api）→ **在概览就地**看到「缺少依赖模组：JEI 需要 fabric-api」→ 点「去添加」→ 来源栏抽屉搜 fabric-api → 添加 → 回概览 → 「重新解析」→ 冲突自动结案（后端 O21 语义），健康分转绿。
6. 进「内容」编排态 → 新建章节「开局」→ 双击空白建节点 → 奖励选物品（复用物品网格）→ 保存草稿 → 校验 → 应用。
7. 顶栏「交付」→ ① 检查通过 → ② 登记版本 + 开始构建 → 产物出现（大小 / sha256）→ 下载按钮可点。
8. ③ 选游戏目录 → 安装（进度条 + 日志流）→ ④ 填离线用户名 → 启动 → 游戏窗口起来。
9. ⑤ 需要发布时点「发布到 Modrinth」；无凭证则按后端语义拒绝并说明原因。

### B｜处理冲突（判断 → 动手，不跳页）

概览红色信号 → 冲突面板展开 → 逐条看 summary/kind/severity → error 级点「去添加依赖」或「忽略」→ warning 级点「忽略」→ 健康分与底部告警数即时更新 → 交付页构建闸门放开。

### C｜顺科技树查物品来源（无限下钻，不换页）

内容页索引态搜「AE2 控制器」→ 点它（设焦点）→ 关系态自动居中 →「怎么合成它」看到配方 → 点材料「充能石英」→ 关系态重新居中 → 继续下钻到原料 → 发现某材料来自**未启用模组** → Inspector「来源模组」→ 来源栏启用它 → 回关系态，路径通了。全程焦点不丢、不刷新、不整页跳转。

### D｜魔改一条配方（读 → 写 → 读）

关系态看着某条配方 → 点「魔改此配方」→ 写态打开，payload 已是这条配方的当前内容（不是空模板）→ 改 JSON，右侧 JEI 预览实时重画 → 存草稿 → 校验（issue 贴到出错行）→ 应用 → **自动回关系态**，该配方带「已魔改」标记，Inspector 的配方计数同步 → 需要撤销时写态「历史」抽屉里回滚。

### E｜魔改顺路生成任务（你问的第 2 条，v2 的核心新增）

承接链路 D 的 apply 成功那一刻：

1. 成功面板除了「回到关系态」，多一个主按钮 **「生成任务节点」**。
2. 点它 → 系统用**已经知道的信息**预填一个节点：
   - 标题 = 「制作 {产物显示名}」
   - 图标 = 产物物品图标（catalog，不再是 emoji 目录）
   - 奖励 = 产物物品 × 配方产出数量
   - 目标任务 = `item` 型，`itemId` = 产物 ID，`count` = 产出数量
   - `modRefs` = 该配方涉及的模组 ID（后端会校验它是否在本包内，`content.go:842-844`）
   - 前置 = 该配方的**材料**中已经存在对应任务节点的那些（按物品 ID 匹配）
   - 章节 = 当前章节；坐标 = 该章节画布空白处
3. 作者只改标题与描述 → 保存草稿 → 校验（环检测 + modRefs 校验）→ 应用。
4. 反向也通：编排态选中一个节点 → Inspector 显示它引用的配方 → 点「看这条配方」→ 关系态居中 → 点「魔改」→ 写态。

**这条链路的判据**：从 apply 到任务节点出现在画布上，作者不需要重新输入任何系统已经知道的字段（产物、数量、图标、模组、材料）。

### F｜出包（一屏走完）

交付页 ① 检查 →（有 error 级冲突则构建按钮禁用 + 「去概览处理」）→ ② 注册导出目录 → 登记版本 → 开始构建 → 产物行出现 → 下载 → ③ 选游戏目录 → 安装 → ④ 启动 → ⑤ 发布。任一段失败，错误显示在该段内，其余段保持可用。

|---|---|---|
| **P1 收口导航 + 换外壳** | 左栏 → 顶栏（全局 2 + 包内 3）；删底边栏并把真实内容搬到右栏「包状况」段；包内路由 10 → 3；旧路由全部重定向并带参数；删孤儿路由与占位假按钮；焦点写进 URL | 顶栏可点导航 = 5、包内 Tab = 3；无底边栏（`grep -rn "app-statusbar" apps/web/src` = 0）；11 条旧路由逐条访问都落到正确的新位置且焦点正确；`grep -rn "后续版本提供" apps/web/src` = 0；刷新页面焦点不丢 |

| 风险 | 应对 |

## 11. 总验收标准

一次点击级验收，全部满足才算 v2 落地：

1. 外壳 = 顶栏（可点导航 5 项：工作台 / 整合包 / 概览 / 内容 / 交付，另有 ⚙ 图标按钮）+ 右栏两段（包状况 / 当前焦点）+ **无底边栏**；包内 Tab = 3。左栏与 `.app-statusbar` 在代码里不存在。
2. 11 条旧路由逐条访问，全部落到正确新位置，焦点与筛选不丢。
3. 从任意物品出发，**不刷新、不丢焦点**即可到达：它的配方、来源模组、引用它的任务节点、以及它的魔改写态。
4. 关系态点材料能持续下钻到原料；下钻 5 层后顶栏 Tab 高亮、右栏焦点、面包屑三者一致。
5. 魔改一条配方 → apply → 关系态立刻显示「已魔改」，无需手动刷新。
6. apply 后一次点击生成任务节点，产物/数量/图标/奖励/前置/modRefs 全部预填（§7-E 判据）。
7. 概览上能逐条 resolve/ignore 冲突，处理后健康分、底部告警数、交付构建闸门三处同步更新。
8. 交付页一屏走完 检查 → 构建 → 下载 → 安装 → 起窗，五段状态各自独立可见。
9. 界面上没有点了没反应的按钮、没有写死的数字、没有拿不到数据却显示成功的块。
10. 任意状态刷新页面，所见完全一致（URL 是单一事实源）。
11. 全仓 `grep -rn "后续版本提供\|敬请期待" apps/web/src` 零命中。
12. `npx tsc --noEmit` 零错误、`npx vite build` 通过、`go test ./... -count=1` 全绿、`scripts/chain-test-run.sh` 不退化（≥ PASS 172 / FAIL 0）。
