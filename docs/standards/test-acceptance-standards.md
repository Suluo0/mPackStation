# mPackStation 测试与验收标准（v0.1）

> 本标准不描述某个具体功能的测试用例，只定义一项变更在什么条件下可以被判定为“验收合格”。适用于代码、数据库、API、构建、部署、配置和文档约束的变更。

## 1. 验收结论

验收只有三种结论：

- **合格**：所有适用门禁通过，证据完整，没有未处置的阻断问题。
- **有条件合格**：仅存在明确记录、不会影响本次交付目标的非阻断问题，并有负责人和处理时点；不得用于架构、安全、数据一致性、迁移和恢复问题。
- **不合格**：任一强制门禁失败、证据缺失，或结论依赖推测而非可重复验证。

“本地看起来正常”“接口返回了 JSON”“构建命令退出码为 0”都不能单独证明验收合格。

## 2. 验收前提

开始验收前必须具备：

1. 明确本次变更范围、预期行为和明确不做的内容。
2. 能指出对应的架构、契约、页面规格、ADR 或缺陷记录。
3. 列出受影响的模块、数据表、API、任务、文件和配置。
4. 标明本标准中哪些门禁适用、哪些不适用；`N/A` 必须写理由。
5. 测试环境、依赖版本、数据目录和执行命令可重现。

范围不清、契约未定或无法说明影响面的变更，不进入正式验收。

## 3. 强制验收门禁

### 3.1 构建与静态检查

合格要求：

- Go 代码完成格式化，`go test ./...`、`go vet ./...` 全部通过。
- 前端依赖通过锁文件安装，TypeScript 检查和生产构建通过。
- 没有新增未解释的编译警告、循环依赖、禁用规则或跳过检查。
- 依赖清单和 lockfile 可重复解析，不依赖开发机上的全局包或隐式环境。
- 生成物不包含源码路径、密钥、临时文件或开发配置。

任一必需构建目标失败即不合格。

### 3.2 自动化测试

合格要求：

- 所有已有测试通过；不得删除、跳过或弱化无关测试来换取通过。
- 新增或修改的业务规则必须有自动化测试覆盖成功、拒绝和边界路径。
- 修复缺陷必须包含能在修复前失败、修复后通过的回归测试。
- 测试必须可独立重复执行，不依赖执行顺序、外部残留数据或人工点击。
- 不允许存在已知 flaky 测试；偶发失败必须先定位并修复，不能通过重复运行挑选成功结果。

代码覆盖率只作为辅助信号，不以单一百分比替代行为覆盖。关键不变量、错误路径和恢复路径必须有直接测试证据。

### 3.3 数据库与迁移

凡涉及数据库，必须同时通过：

- 空数据库升级到最新版本。
- 上一已发布版本升级到最新版本。
- 重复启动不会重复执行或破坏 migration。
- migration checksum、`quick_check` 和 `foreign_key_check` 通过。
- FK、CHECK、UNIQUE 和事务回滚行为符合架构不变量。
- 迁移失败时不留下半应用 schema；已有数据不被静默丢失或错误改写。
- 已应用 migration 文件未被修改，schema 变化由新 migration 引入。

无法证明升级安全的数据结构变更不得验收。

### 3.4 API 与契约

凡涉及 API，必须同时通过：

- 请求、成功响应、错误信封、HTTP 状态码和 request-id 与契约一致。
- 前端 zod schema 可以解析真实 fixture；mock 与真实响应语义一致。
- 非法参数、资源不存在、状态冲突、超限和内部失败返回稳定错误码。
- 分页、排序、过滤和幂等行为可重复验证。
- 不泄漏绝对路径、SQL、内部栈、密钥或上游凭据。
- 旧客户端仍可处理只增字段的兼容变更；破坏性变化必须经过版本化或 ADR 评审。

只验证成功响应、不验证错误语义的 API 不得验收。

### 3.5 状态、任务与恢复

凡涉及异步任务或持久状态，必须同时通过：

- 合法状态迁移成功，非法迁移被拒绝。
- 重复提交不会产生未定义重复副作用。
- 取消、失败、重试、超时和服务退出后的行为明确且可验证。
- 服务在任务执行中被终止后，重启可以恢复或明确失败，不遗留永久假 `running`。
- 旧 lease/epoch 的 worker 无法继续写入状态、业务数据或日志。
- 数据库状态、任务事件、outbox 和文件副作用最终一致。

仅验证正常完成、不验证取消和恢复的任务功能不得验收。

### 3.6 文件与磁盘一致性

凡涉及文件写入、导入、缓存或产物，必须同时通过：

- 文件操作遵守 `temp → 校验 → 事务登记 → rename` 或架构规定的等价流程。
- 中途失败和进程退出不会留下可被误认为有效的半成品。
- 数据库有记录但文件缺失、文件存在但数据库无记录时，巡检行为可验证。
- 删除操作不会误删仍被引用的共享文件。
- 磁盘不足、权限不足、路径非法和目标已存在时返回稳定失败结果。
- 测试产生的临时文件可清理，不污染仓库或用户数据目录。

### 3.7 安全边界

凡涉及 HTTP、路径、上传、导入、密钥或外部请求，必须验证：

- 缺失或错误 token 的受保护请求被拒绝。
- 非法 Host、Origin、Content-Type 和请求体大小被拒绝。
- 路径穿越、绝对路径越界、符号链接/junction 逃逸被拒绝。
- 归档穿越、压缩炸弹、超大条目、超多条目和危险链接被拒绝。
- URL 导入或外部回调不能访问回环、私网、link-local 或重定向越界目标。
- 密钥、token 和敏感字段不出现在日志、错误、任务 payload、activity 或普通响应中。
- 限流、超时和资源上限不会因异常请求被绕过。

发现可复现的未授权写入、任意文件访问、凭据泄漏或安全边界绕过，一律不合格。

### 3.8 健壮性与资源行为

合格要求：

- 请求和外部调用均有明确 timeout/cancel 行为。
- 服务可优雅退出；退出超时后仍能依靠重启恢复保持一致。
- Provider 的 404、429、5xx、超时、断网、熔断和缓存回退行为已验证。
- 磁盘不足、数据库 busy、文件占用和上游不可达不会导致 panic 或静默数据损坏。
- 并发提交、重复请求和取消竞争不会破坏不变量。
- 没有明显无界 goroutine、无界队列、无界内存或无界日志增长。

### 3.9 可观测性

合格要求：

- 关键请求具有 request-id；任务具有 task-id，包相关操作具有 pack-id。
- 成功、拒绝、失败和恢复事件能通过结构化日志或审计定位。
- 错误日志包含可行动的 component、operation 和 error_code，但不包含敏感信息。
- 新增长时间运行或外部依赖能力时，补充相应任务/Provider/失败指标。
- 用户可见状态与内部日志语义一致，不出现“界面成功但后台失败”而无记录的情况。

### 3.10 部署与升级

达到阶段交付或发布条件时，必须验证：

- 在干净目录安装依赖、构建、初始化、启动、探活和关闭成功。
- 不依赖源码目录、开发服务器或开发机缓存即可运行。
- 默认数据目录、配置、日志和端口符合项目规范。
- 已有数据库和配置升级后可正常启动；失败时给出可执行提示。
- 重复安装/启动不会覆盖用户数据或产生多个写实例。
- 分发包版本、构建信息和依赖锁定信息可追溯。

## 4. 缺陷放行标准

缺陷按影响分级：

- **P0 阻断**：数据损坏、任意文件访问、凭据泄漏、无法启动/升级、核心流程完全不可用。
- **P1 阻断**：主要流程错误、任务不可恢复、错误授权、错误构建产物、稳定复现的崩溃。
- **P2 条件阻断**：存在规避方式的次要功能错误、明显性能退化、错误提示不可行动。
- **P3 非阻断**：不影响正确性和可用性的视觉、文案或轻微交互问题。

放行规则：

- P0、P1 必须为 0。
- P2 默认必须修复；确需延期时必须记录影响、规避方法、负责人和处理时点。
- P3 可以进入收工清单，但不能掩盖功能、契约或可访问性问题。
- 安全、数据一致性、迁移和恢复缺陷不得以“有条件合格”放行。

## 5. 验收证据包

每次正式验收至少保存：

1. 变更范围和适用门禁清单。
2. 实际执行命令、退出码和关键输出。
3. Go、Node、依赖锁文件和操作系统信息。
4. 单元、集成、契约、安全和 E2E 测试结果。
5. migration 起点、终点和完整性检查结果。
6. 必要的日志、截图、fixture 或产物校验值。
7. 已知问题、缺陷等级、延期理由和负责人。
8. 最终验收结论及其依据。

证据必须来自当前提交/工作树和当前测试环境。旧截图、旧命令输出或其他分支的成功结果不能证明本次验收通过。

## 6. 最终合格判定

只有同时满足以下条件，才允许标记“验收合格”：

- 所有适用强制门禁通过。
- 所有测试结果可重复，且没有 flaky、跳过或被弱化的关键测试。
- P0/P1 缺陷为 0，P2 已处理或按规则批准延期。
- 架构、API、migration、前端 schema 和实现保持一致。
- 数据、任务和文件在成功、失败、取消和重启路径下保持一致。
- 安全边界没有已知绕过。
- 验收证据包完整，可由另一名开发者在干净环境复核。

任何一项证据缺失，都只能判定为“尚未证明合格”，不能按默认通过处理。
